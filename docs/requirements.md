# Dineary 고객 요구사항

이 문서는 고객이 원하는 기능, 서비스 정책, 문제 발생 시 기대하는 동작을 정의한다. 현재 프로토타입의 구현 완료 목록은 아니다. Redis 캐시·분산 락은 고객이 지정한 기술 활용 조건이며, ERD·테이블·API·모듈·배포 구조 등의 상세 설계는 개발 단계에서 결정한다.

식별자는 `분류 문자 + 번호`로 표기한다. 예: A1, B1, P1. 문서 순서가 바뀌어도 부여한 식별자는 유지한다.

| 분류 | 의미 |
| --- | --- |
| A | Account — 회원·인증 |
| B | Browse — 음식점 탐색 |
| R | Review — 리뷰·취향 기록 |
| S | Service — 예약·알림·운영 |
| P | Performance — 성능·캐시 안정성 |
| C | Coupon — 할인 쿠폰·동시 요청 |
| Q | Quality — 사용성·서비스 품질 |

## A. 회원·인증

**A1 - 이메일·비밀번호로 계정을 만들고, 서비스에서는 닉네임으로 활동한다.**

- 가입 시 이메일·비밀번호·비밀번호 확인·닉네임을 입력한다.
- 이메일은 로그인·인증·계정 복구에 사용하며, 리뷰 등 공개 활동에는 닉네임을 표시한다.
- 비회원은 음식점을 탐색할 수 있다. 리뷰 작성·가게 저장·예약·쿠폰 발급은 인증을 완료한 회원만 이용한다.
- 닉네임 변경으로 기존 기록의 소유자가 달라지지 않아야 한다.

**A2 - 같은 이메일의 중복 가입과 타인·존재하지 않는 이메일을 이용한 가입을 방지한다.**

- 동일 이메일로 활성 계정이 여러 개 만들어지지 않아야 하며, 동시에 가입 요청을 보내도 동일하게 적용한다.
- 이메일 형식 검사는 입력 오류를 찾는 용도로 사용한다. 실제 사용 가능한 이메일의 소유 여부는 해당 주소로 보낸 인증 링크 또는 인증번호로 확인한다.
- 인증 전에는 가입 대기 상태로 두고 회원 활동을 허용하지 않는다. 미인증 요청은 정해진 기간 후 만료시켜 이메일을 무기한 선점하지 못하게 한다.
- 인증 수단은 유효시간과 사용 횟수를 제한한다. 만료·사용된 인증 수단은 재사용할 수 없어야 한다.
- 가입·로그인·비밀번호 재설정에서 동일한 이메일 비교 정책을 적용한다. 서로 다른 주소를 임의로 같은 계정으로 합치지 않는다.
- 다른 사람이 만든 미인증 가입 요청으로 기존 계정의 비밀번호·소유권을 변경할 수 없어야 한다.

이메일 소유 확인과 일회성·기간 제한 인증의 근거: [OWASP 이메일 검증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html).

**A3 - 가입 여부 조회, 인증 메일 폭탄, 비밀번호 대입 공격으로부터 회원을 보호한다.**

- 가입·로그인·계정 복구의 응답 문구·처리 방식 차이로 특정 이메일의 가입 여부를 쉽게 알아낼 수 없게 한다. 중복 여부는 서비스 내부에서 검사한다.
- 이메일·접속 출처·전체 서비스 기준으로 가입, 인증 요청, 재발송, 인증번호 입력, 로그인 시도 횟수를 제한한다.
- 재발송 대기시간과 메일 발송 총량 제한을 두고, 반복 실패·반송 주소에 대한 무제한 발송을 막는다.
- 의심스러운 반복 요청에는 추가 확인 또는 일시 제한을 적용하되, 타인의 반복 요청만으로 정상 계정이 영구 잠기지 않게 한다.
- 인증 실패·메일 지연 시 재시도 방법을 안내하고, 비밀번호·인증번호·인증 링크가 공개 화면이나 기록에 노출되지 않게 한다.

가입 여부 노출 방지와 로그인 공격 대응의 근거: [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

**A4 - 로그인·로그아웃·계정 복구·탈퇴 및 본인의 활동 내역을 관리한다.**

- 새로고침 후에도 정해진 기간 동안 로그인을 유지하고, 로그아웃·만료 후에는 회원 기능을 이용할 수 없게 한다.
- 비밀번호 재설정은 이메일 소유 확인 후 진행한다.
- 마이페이지에서 프로필·취향·내 리뷰·저장한 가게·컬렉션·예약·쿠폰을 관리한다.
- 다른 계정의 개인 기록을 조회·변경할 수 없게 하고, 탈퇴 시 개인정보와 공개 콘텐츠의 처리 정책을 안내한다.

## B. 음식점 탐색

B1 - 음식점 목록·상세·기본 검색을 제공하고, 주소·위치·메뉴·가격·사진·영업시간·휴무일·편의시설·평점·리뷰를 함께 확인할 수 있게 한다.

B2 - 가게명·지역·메뉴·음식 종류 검색, 조건별 필터·정렬·페이지 구분, 자동완성·오타·동의어 처리 및 최근·인기 검색어를 제공한다.

B3 - 현재 위치·선택 지역·반경 기준 주변 음식점과 거리를 표시하고 지도·목록을 연동한다. 위치 권한이 없으면 지역을 직접 선택할 수 있게 한다.

B4 - 지역·음식 종류별 인기 순위와 취향·위치·활동 이력 기반 추천을 제공하고, 이용 이력이 없는 사용자에게도 기본 추천을 제공한다.

## R. 리뷰·취향 기록

R1 - 별점·방문일·내용·사진을 포함한 리뷰 작성·수정·삭제, 리뷰 조회·정렬·도움돼요·신고 기능을 제공하고 변경 사항을 평점·리뷰 수에 반영한다.

R2 - 리뷰 작성 자격·재방문 리뷰·광고성 콘텐츠·랭킹 반영 기준을 정하고, 중복 리뷰·스팸·별점 조작에 대응한다.

R3 - 음식점을 저장·해제하고 주제별 컬렉션을 생성·편집·공유하며, 컬렉션의 공개 범위를 설정할 수 있게 한다.

## S. 예약·알림·운영

S1 - 날짜·시간·인원별 예약 가능 여부 조회와 신청·확정·취소·방문 완료·노쇼 처리를 제공한다. 동시 신청에도 정원 초과·중복 예약이 발생하지 않아야 한다.

S2 - 예약 상태 변경·리뷰 반응·쿠폰 발급 결과를 알리고, 알림 목록·읽음 상태·수신 설정을 제공한다.

S3 - 소유 확인을 마친 사장님이 음식점 정보·메뉴·영업시간·예약 정원을 관리하고 리뷰에 답글을 작성할 수 있게 한다.

S4 - 관리자가 회원·음식점·리뷰·이벤트를 관리하고, 음식점 등록·중복 병합·이전·폐업·정보 오류·신고·이의제기·이용 제한을 처리하며 주요 처리 이력을 확인할 수 있게 한다.

## P. 성능·캐시 안정성

**P1 - 평점이 높거나 인기 있는 음식점의 조회 결과를 Redis에 캐시하여 빠르게 제공한다.**

- 자주 조회되는 음식점 상세·평점 요약·인기 목록을 우선 대상으로 한다. 높은 평점과 많은 리뷰·저장·조회 중 무엇을 인기 기준으로 사용할지는 별도 합의한다.
- 원본 정보는 영구 보관하고 캐시는 다시 만들 수 있는 조회용 사본으로 사용한다.
- 리뷰·메뉴·가격·영업 상태가 바뀌면 합의된 시간 안에 캐시에도 반영한다. 삭제·이용 제한된 콘텐츠가 캐시 때문에 계속 노출되지 않게 한다.
- 목록 순위를 위한 약간의 갱신 지연과 달리, 예약·쿠폰의 최종 가능 여부는 오래된 캐시만으로 확정하지 않는다.

**P2 - 캐시 관통: 존재하지 않는 음식점을 반복 조회해도 원본 저장소에 부하가 계속 전달되지 않게 한다.**

- 잘못된 요청을 먼저 거르고, 같은 없는 항목에 대한 반복 조회를 줄이며 과도한 요청을 제한한다.
- 대응 후보는 짧은 기간의 ‘조회 결과 없음’ 캐시 등이다. 대량의 서로 다른 잘못된 요청에도 대응해야 한다.
- 이후 실제 음식점이 등록되면 기존의 ‘없음’ 결과 때문에 장시간 검색·조회에서 누락되지 않아야 한다.

**P3 - 캐시 눈사태: 많은 캐시가 함께 만료되거나 Redis에 장애가 나도 서비스 전체가 연쇄적으로 중단되지 않게 한다.**

- 캐시 만료 시점을 분산하고 주요 인기 데이터를 미리 준비하는 방안을 검토한다.
- Redis 장애 시 모든 요청을 제한 없이 원본 저장소로 보내지 않는다. 처리량을 제한하고, 허용된 이전 결과 또는 일시 지연 안내를 제공한다.
- 복구 직후에도 캐시를 한꺼번에 다시 만들지 않도록 하여 재차 과부하가 발생하는 것을 막는다.

**P4 - 캐시 붕괴: 특정 인기 음식점의 캐시가 만료되어도 같은 정보를 동시에 대량으로 다시 조회하지 않게 한다.**

- 같은 항목의 갱신 요청을 조정하여 한 작업이 갱신하는 동안 나머지는 짧게 대기하거나 허용된 이전 결과를 받게 한다.
- 갱신 작업이 실패하거나 지연되어도 요청이 무한 대기하지 않아야 한다.
- 문서에서는 ‘많은 항목의 동시 만료’를 눈사태, ‘하나의 인기 항목 만료에 요청 집중’을 붕괴로 구분한다.

관통·요청 폭주 대응 참고: [Redis 캐시·요청 폭주 대응](https://redis.io/blog/how-to-tame-the-thundering-herd-problem/). 인기 항목의 중복 갱신 억제 참고: [Redis 캐시 갱신 보호](https://redis.io/docs/latest/develop/use-cases/cache-aside/java-jedis/). 구체적인 조합은 개발 단계에서 검증한다.

**P5 - 캐시의 속도 개선과 장애 대응을 확인할 수 있어야 한다.**

- 캐시 적용 전후 응답시간과 원본 조회량을 비교한다.
- 없는 항목 반복 조회, 대량 만료, 인기 항목 만료, Redis 중단 상황에서 오류·응답 지연·원본 부하를 확인한다.
- 목표 접속량·응답시간·허용 갱신 지연은 임의로 확정하지 않고 서비스 규모와 함께 합의한다.

## C. 할인 쿠폰·동시 요청 — 향후 확장

**C1 - 음식점 할인 쿠폰과 수량 한정 이벤트를 운영한다.**

- 대상 음식점·할인 금액 또는 할인율·최소 주문 조건·사용 기간·발급 수량·회원별 발급 한도를 설정한다.
- 사용자는 이벤트 일정·조건·진행 상태와 본인의 발급·사용·만료 내역을 확인한다.
- 할인 한도·중복 할인·사용 취소 시 복구 여부와 오프라인 사용 확인 방식은 이벤트 도입 전에 합의한다.

**C2 - 티켓팅처럼 동시 신청이 몰려도 쿠폰을 중복·초과 발급하지 않는다.**

- 이벤트 시작 전에는 발급하지 않고, 정해진 수량이 소진되면 마감한다.
- 동일 회원의 반복 클릭·여러 기기 신청·응답 지연 후 재시도에도 발급 한도를 지킨다.
- 요청이 처리됐지만 응답을 받지 못한 사용자는 발급 내역에서 최종 결과를 확인할 수 있어야 한다.
- 하나의 쿠폰을 동시에 여러 번 사용하려 해도 사용 완료는 한 번만 처리한다.
- ‘계정당 1장’은 ‘사람당 1장’과 다르다. 이메일 인증만으로 다계정 사용자를 완전히 구별할 수 없으므로 추가 부정 발급 정책은 별도 합의한다.

**C3 - 여러 서버에서 처리하는 쿠폰 발급에 Redis 분산 락을 활용하여 동시성 제어를 검증한다.**

- 같은 이벤트의 수량·발급 한도를 동시에 변경하는 요청을 조정하되, 다른 이벤트까지 불필요하게 대기시키지 않는다.
- 락 보유 서버의 중단·처리 지연·락 만료 후에도 중복·초과 발급이 발생하지 않아야 한다.
- 락을 얻지 못한 요청에는 대기·재시도·마감 중 실제 상태에 맞는 결과를 제공한다.
- Redis 락만으로 모든 장애 상황의 정확성을 보장한다고 가정하지 않는다. 최종 발급 결과의 검증과 복구까지 요구하며, 상세 보장 방식은 개발자가 설계한다.

여기서 말하는 기능은 ‘분할 락’이 아닌 ‘분산 락’이다. 락의 유효시간·장애 조건을 고려해야 하는 근거: [Redis 분산 락 문서](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

**C4 - 이벤트 접속 폭주 시 대기·요청 제한으로 서비스를 보호한다.**

- 분산 락은 같은 쿠폰 자원의 동시 변경을 조정하는 수단이며, 접속자 전체의 대기열을 대신하지 않는다.
- 수용 가능한 처리량을 넘으면 대기 상태·재시도 시점·마감 여부를 안내하고, 반복 클릭·새로고침으로 중복 대기하거나 순서를 앞지를 수 없게 한다.
- ‘선착순’은 사용자 기기의 클릭 시각이 아닌 서비스가 접수한 순서 등 합의된 기준으로 판정한다. 락 획득 순서를 곧바로 선착순으로 간주하지 않는다.
- 결과를 확정할 수 없는 장애 중에는 발급을 제한하고 상태를 안내한다. 복구 후 기존 발급 결과를 확인하여 중복 처리하지 않는다.

**C5 - 한정 쿠폰의 동시성 처리 결과를 재현 가능한 시나리오로 확인한다.**

- 검증 예시: 재고 100장·회원당 1장 이벤트에 서로 다른 인증 회원 1,000명이 동시에 신청해도 성공 발급은 최대 100장이고 중복 발급은 없어야 한다.
- 정상 처리로 재고가 모두 소진되면 발급 내역과 잔여 수량이 일치해야 한다. 장애 중 보류된 요청은 최종 결과로 정리되어야 한다.
- 동일 회원의 중복 요청, 처리 중 서버 중단, 락 만료, Redis 장애, 쿠폰 중복 사용도 함께 확인한다.
- 위 숫자는 기능 검증 예시이며 실제 동시 접속 보장 수치나 확정된 이벤트 정책이 아니다.

## Q. 사용성·서비스 품질

Q1 - 모바일·데스크톱에서 주요 기능을 이용하고 키보드로 조작할 수 있게 하며, 로그인 필요·로딩·빈 결과·오류·대기·재시도 상태를 명확히 안내한다.

Q2 - 개인정보·위치·활동 이력의 수집 목적·공개 범위·보관·삭제 정책을 안내하고, 다른 회원의 비공개 정보나 인증 정보가 노출되지 않게 한다.

Q3 - 서비스 장애와 주요 처리 실패를 운영자가 파악할 수 있게 하고, 복구 과정에서 회원 기록·예약·쿠폰이 유실되거나 중복 처리되지 않도록 한다.
